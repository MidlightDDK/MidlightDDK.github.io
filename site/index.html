01 RAG · Retrieval & grounding

FilingLens

Citation-verified Q&A over SEC 10-K filings. Every answer sentence cites the passage it came from, sentences the sources don't support are flagged, and questions the filings can't answer are declined.

What I built

  • Python ingestion of 24 filings from 12 companies with structure-aware chunking, then hybrid search: BM25 and dense embeddings fused with Reciprocal Rank Fusion, plus company and fiscal-year filters.
  • A deterministic verifier that runs in the browser: a sentence is verified only if it cites a passage and every number in it appears there. An optional AI judge agrees with reference labels 95.5% of the time (κ 0.86).
  • A Cloudflare Worker gateway with a provider fallback chain (Workers AI → Groq → Gemini), a KV answer cache, a Turnstile bot check, and rate limits. It runs for $0, with no vector database.
  • A 211-question eval set, split dev/test before tuning. CI fails any push that drops recall@10 by more than 2 points.

What didn't work: a cross-encoder reranker lowered recall@10 by 5 points on test and took about 7 s per query in WASM, so it stayed out of production.

Browser Analyst

A data-analyst agent that writes and runs SQL and Python in your browser, repairs its own errors, draws charts, and links every number in its answer to the result cell that produced it. Your file never leaves the tab.

What I built

  • An agent loop that runs SQL in DuckDB-WASM and Python in Pyodide, both in Web Workers. Results stay in the tab; the model sees only schemas, profiles, and 20-row previews.
  • Layered defenses: a read-only SQL guard (65 unit cases), engine lockdown, approval before any Python runs, spotlighting plus an injection detector, and a Content-Security-Policy as egress control.
  • A reproducible benchmark with cached model calls, full traces, and token accounting. The CI gate blocked a prompt change that passed every unit test but dropped the smoke split to 8/15.
  • A tier-0 cascade test with my own fine-tuned model (PocketSQL): 30% fewer LLM calls but 8 points lower success, so the live app doesn't use it.

What didn't work: knowing when to ask. On 8 deliberately ambiguous questions, models asked for clarification at most 3 times. It's the weakest category, and the README reports it rather than hiding it.

03 Fine-tuning · On-device inference

PocketSQL

A 0.5B text-to-SQL model I fine-tuned with LoRA and shipped to the browser. It writes DuckDB SQL on your GPU through WebGPU, costs $0 per query, and keeps working with Wi-Fi off.

What I built

  • The dataset: 7,376 Spider pairs converted to DuckDB and kept only when results match SQLite, plus 591 synthetic pairs kept only when independent models' queries agree.
  • A LoRA fine-tune of Qwen2.5-Coder-0.5B with PyTorch, TRL, and PEFT, merged and exported to 4-bit ONNX (q4f16 for WebGPU, q4 for WASM). The fp32 export matches PyTorch on 20/20 parity prompts.
  • A release gate: a model ships only if the exact file the browser downloads beats the base model and the previous release. A weekly job re-checks it, and an offline end-to-end test loads the real model, cuts the network, and answers.
  • A local-first cascade: on Spider dev it beats a 120B API model alone (75% vs 73%) with 59% fewer API calls.

How I work

Engineering habits that transfer to your team

A demo that works once is easy. These are the habits that keep AI features correct after launch, each backed by a project above.

  1. Measure on held-out data

    I split eval sets before tuning and keep test data out of training; PocketSQL checks for leakage in CI. FilingLens' test split ran exactly once, for the release numbers.

  2. Gate quality in CI

    Retrieval recall, agent success, and model accuracy all have regression gates. One caught a prompt edit that passed every unit test but cut agent success nearly in half.

  3. Design for untrusted input

    Prompt injection is a given. I layer SQL guards, execution approval, spotlighting, and CSP egress control, then red-team each defense on its own.

  4. Ship it, then keep it running

    All three apps are live, with daily smoke tests that open an issue on failure. Browser Analyst's build fails if first-load JavaScript passes 300 KB, and two of the apps score 99 on Lighthouse's mobile performance audit.

  5. Keep costs honest

    In-browser retrieval and inference, provider fallback chains, and answer caching mean all three run for $0/month, and degrade gracefully when free quotas run out.

  6. Report what didn't work

    A reranker that hurt recall, a training run the gate rejected, a model that wouldn't ask for clarification: I write down failures so the next decision is better.
